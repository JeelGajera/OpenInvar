# Evaluation — 2026-09-14

OpenInvar 0.2.0, measured against the criteria fixed in
[`criteria.md`](../criteria.md) before the run.

**Verdict: CONTINUE.** No hard criterion failed. One criterion turned out not
to measure what it was written to measure, which is recorded below rather than
quietly scored as a pass.

## Corpus

Four real repositories, chosen for being ordinary rather than flattering:
widely used, actively maintained, and written before OpenInvar existed, so
nothing in them was shaped to suit it. Eight consecutive commits each.

| Repository | Language | Files | Edges | Slowest revision |
|---|---|---|---|---|
| [rust-lang/log](https://github.com/rust-lang/log) | Rust | 23 | 388 | 0.08s |
| [spf13/cobra](https://github.com/spf13/cobra) | Go | 66 | 1,870 | 0.16s |
| [pallets/click](https://github.com/pallets/click) | Python | 177 | 1,476 | 0.22s |
| [google/gson](https://github.com/google/gson) | Java | 313 | 18,989 | 0.71s |

32 revisions, 28 consecutive commit pairs.

## Results

### D — Determinism · **PASS**

**32 of 32 revisions byte-identical.** Zero mismatches.

Each revision was analysed twice, into two temporary worktrees on different
paths, and the JSON documents compared byte for byte. Two runs landing on
different paths is the point: a path leaking into the output fails here rather
than staying invisible.

This is the criterion with no tolerance, and the one everything else depends
on. It held across four languages and four build systems.

### P — Precision · **PASS**

**0 of 28 commit pairs produced an error-severity finding.** Threshold was
≤ 10%.

These are commits reviewed and merged by the maintainers of four healthy
projects, so the overwhelming majority are ordinary work. All four detectors
ran on every pair — `test-tampering`, `assertion-removal`, `contract-erosion`
and `dead-on-arrival` — and none fired.

Zero warn-severity findings as well, which is worth noting because
`dead-on-arrival` is the loosest detector in the set.

**What this does and does not show.** It shows the detectors do not cry wolf on
ordinary work, which is the property that decides whether a gate stays switched
on. It does **not** show they catch real tampering: without labelled examples
there is no recall figure here, and precision without recall is half the
picture. Saying so is better than implying otherwise.

### R — Resolution coverage · **the criterion was wrong**

Median reported coverage was 100.0%, which scores as a pass against the ≥ 90%
threshold. It should not be read as one.

`dispatch::run_adapter` stamps **every** Tier 1 edge `Resolution::Resolved`,
because a Tier 1 pipeline is defined as one that bound its targets. The
coverage figure counts resolved edges. So a repository containing no Tier 2
files reports 100% *by construction* — the number cannot come out any other
way, and measuring it on more repositories would not change that.

The figure is not meaningless: it separates Tier 1 from Tier 2 regions, and on
a polyglot repository it correctly reports the structural share (OpenInvar
itself reads 99.8%, naming its 14 structural edges). But it says nothing about
references *dropped inside* a Tier 1 file, which is what the criterion was
trying to capture.

**An independent check, since the tool's own metric could not answer it.**
Counting `import` statements in gson's source and comparing against recorded
`Imports` edges:

```
source 'import' statements : 2432
recorded Imports edges     : 2432
```

Exactly one-to-one across 313 Java files — measured against the source text
rather than against anything OpenInvar reports about itself. Nothing was
dropped at the import level.

That is one edge kind on one repository, so it is evidence rather than proof.
The honest position is that **import resolution is verified complete on this
corpus, and reference-level drop rate remains unmeasured.**

**What would fix this.** The adapters know when they drop a reference — the
Java resolver's rule is literally *resolve it, or do not emit it*. A counter of
attempted-versus-bound references, reported alongside coverage, would make the
real number observable. That is a product change, not an evaluation change, and
it is the main thing this run surfaced.

### T — Performance · **PASS**

Slowest revision **0.71s** (gson, 313 files, 18,989 edges). Median 0.17s.
Threshold was ≤ 60s.

Comfortably inside what a pre-commit hook or a CI step can absorb, with two
orders of magnitude of headroom before the threshold.

## What this run changed

The evaluation's one substantive finding is that criterion R does not measure
what it claims to. It was written believing resolution coverage was a
measurement; it is a tier classification. The criterion is left as written in
`criteria.md` rather than edited after the fact — moving a threshold to match
an outcome is exactly what pre-registering it is meant to prevent — and a
replacement is proposed for the next run:

> **R′** — of the references an adapter attempted to bind, the share it bound.
> Requires the adapters to count attempts and drops, which they currently do
> not.

## Reproducing

```bash
cargo build --release
python3 eval/run.py --commits 8 --out eval/results/run.json
python3 eval/summarise.py eval/results/run.json
```

The run clones into a temporary directory and removes each repository after
measuring it. Network access to github.com is required.
