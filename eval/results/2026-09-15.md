# Evaluation — 2026-09-15

OpenInvar 0.2.0, measured against the criteria fixed in
[`criteria.md`](../criteria.md) before the run. The second run, and the first
able to score **R′** — the replacement criterion the previous run registered
after finding that R did not measure what it was written to measure.

**Verdict: CONTINUE.** No criterion reached its stop threshold. **R′ came in at
63.2% against a 65% pass line, which is the investigate band**, and that
investigation is recorded below rather than the threshold being moved to fit
the result.

## Corpus

Unchanged from the previous run, deliberately: the same four repositories at
the same eight commits each, so the two runs are comparable.

| Repository | Language | Files | Edges | Slowest revision |
|---|---|---|---|---|
| [rust-lang/log](https://github.com/rust-lang/log) | Rust | 23 | 388 | 0.05s |
| [spf13/cobra](https://github.com/spf13/cobra) | Go | 66 | 1,870 | 0.09s |
| [pallets/click](https://github.com/pallets/click) | Python | 177 | 1,476 | 0.14s |
| [google/gson](https://github.com/google/gson) | Java | 313 | 18,989 | 0.41s |

32 revisions, 28 consecutive commit pairs.

## Results

### D — Determinism · **PASS**

**32 of 32 revisions byte-identical**, each analysed twice into worktrees on
different paths. Zero mismatches, as in the previous run.

### P — Precision · **PASS**

**0 of 28 commit pairs produced an error-severity finding**, against a ≤10%
threshold. No warn-severity findings either.

### R — Resolution coverage · **PASS, and still not meaningful**

Median 100.0%, and every one of the four repositories reported exactly 100.0%.

That uniformity is the point, and it is why this criterion was superseded. The
figure counts `Resolution::Resolved` edges; `dispatch` stamps every Tier 1 edge
`Resolved`; none of these four repositories contains a Tier 2 file. 100% was
guaranteed before the run started. Left in place and scored so the two runs
stay comparable, but it carries no information about these repositories.

### R′ — Reference-level coverage · **INVESTIGATE**

Median **63.2%**, against a pass line of 65% and a stop line of 50%.

| Repository | Language | Bound | Attempted | Bound % | Edge-level (R) |
|---|---|---:|---:|---:|---:|
| rust-lang/log | Rust | 388 | 764 | **50.8%** | 100.0% |
| pallets/click | Python | 1,476 | 2,371 | 62.3% | 100.0% |
| google/gson | Java | 18,989 | 29,590 | 64.2% | 100.0% |
| spf13/cobra | Go | 1,870 | 2,836 | 65.9% | 100.0% |

The right-hand column is the whole reason R′ exists. Every repository reports
100% by the old measure and between 50.8% and 65.9% by the new one.

**The investigation.** `log` is the low scorer and the one nearest the stop
line, so it is the one worth opening. Of its 376 unbound references, 51 carry a
resolution diagnostic naming the type, and every single one is Rust's standard
library:

```
 23  From          2  Default        1  AsRef
  6  Display       2  Formatter      1  DebugList / DebugMap / DebugSet / DebugTuple
  3  PartialEq     1  Bencher
  3  PartialOrd
```

`log` is a 23-file crate that is largely `impl` blocks for standard traits, so
a large share of what it names lives outside it by construction. The remaining
unbound references are calls, which are deliberately not diagnosed — prelude
names, macro-generated calls, and fully-qualified paths used without a `use`,
all three of them limits the README already documents.

**So the shortfall is dominated by references to code outside the repository,
which is what the criterion itself anticipated:** *"An unbound reference is not
necessarily a defect: a type from a package whose source was never analysed is
indistinguishable, to an adapter, from one it should have found and missed."*

**What that does and does not license.** It does not license moving the
threshold. 65% was written down before any number existed precisely so that a
result slightly under it could not be re-described as a pass, and 63.2% is
under it. What it licenses is the reading that R′ is behaving as designed — an
upper bound on what is absent — and that the gap between it and R is real
information rather than a regression.

**What would sharpen it.** R′ cannot currently separate "outside the
repository" from "missed", and until it can, the number is a ceiling rather
than a defect count. Splitting the two needs each adapter to say *why* it could
not bind — a language builtin and a third-party package are already
distinguishable in several adapters, a name that simply was not found is not.
That is the next product change this evaluation points at, and it is what would
let a future run judge the figure rather than bound it.

### T — Performance · **PASS**

Slowest revision **0.41s** (gson, 313 files, 18,989 edges). Median 0.10s.
Threshold was ≤ 60s.

Faster than the previous run at every size — 0.71s to 0.41s on gson — with no
performance work in between. Not investigated; noise or machine, and the
headroom is two orders of magnitude either way.

## What changed since the previous run

The previous run's one substantive finding was that R measured a tier
classification rather than a resolution rate. That produced three merged
changes:

- adapters now count the references they could not place, and `status` reports
  both figures side by side
- an unresolved reference can no longer reach the graph stamped gate-safe
- R′ registered in `criteria.md`, with thresholds fixed before this run

This run is the first that could score it, and the first where the headline
number says something about the repositories rather than about how the tool
classifies its own edges.

## Reproducing

```bash
cargo build --release
python3 eval/run.py --commits 8 --out eval/results/run.json
python3 eval/summarise.py eval/results/run.json
```

The run clones into a temporary directory and removes each repository after
measuring it. Network access to github.com is required.
